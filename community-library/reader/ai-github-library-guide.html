不会编程，也能和 AI 一起建设数字图书馆

从知识整理到协作出版：普通人也能参与的数字图书馆。

这本小书不是编程教材。它想回答一个更实际的问题：在 AI 时代，一个普通人怎样参与知识整理、写作、审核与出版，让有价值的资料可以被更多人阅读，也可以被后来的人继续改进？

为什么普通人也值得认识 GitHub？

写一篇文章不难，难的是让它在半年、一年之后仍然找得到、改得动、查得清。如果一份学习资料需要不断补充来源、纠正错误、邀请别人参与，单纯把最终稿发出去还不够。

GitHub 是保存文件、记录修改和组织协作的平台。它最常用于程序开发，但文字、学习笔记、公开资料目录也可以存放在其中。一个 Repository（仓库）可以保存文章和历史版本；Commit（提交）记录一次修改；Issue 可以收集建议；Pull Request 则让维护者在接受修改前先审阅。这些名词不用一次学会，重要的是理解：资料可以持续改进，而不必每次推倒重来。

例如，一份关于志愿服务的中文导读，最初只有基本定义。后来读者指出一个翻译不够准确，另一位读者补充了原始英文来源。编辑可以逐次修订，并保留修改记录。GitHub 的价值就在这样的长期维护中。

AI 让知识整理变得容易，但没有替我们判断

过去，阅读英文资料、归纳重点、写成中文、整理格式，往往需要不同技能。现在，即使英文不熟练，也可以请 AI 先解释术语、整理结构、比较两段文字的差异，或把一份初稿改成更清楚的中文。

但 AI 写得流畅，不代表它说得正确。特别是法律、政策、历史、医学等资料，必须回到原始来源核对。一个可靠的做法是先找到原发布机构的资料，再请 AI 帮忙阅读，而不是让 AI 凭空生成所谓“官方结论”。

请根据我提供的资料，整理一篇适合普通读者的中文导读。区分原文事实、你的解释与尚待核实的问题；保留机构名称、英文术语和原文链接。不要编造引述、日期或数字。

这不是需要背诵的神奇提示词，只是把任务说清楚：读什么、写给谁、哪些地方不能猜。没有付费 AI 工具的人，也可以只负责找来源、提问题或校对文字；参与知识整理不以订阅某项服务为前提。

一本数字图书怎样从资料变成作品？

假设想制作一本《初识社区志愿服务》的小书。首先确定读者真正关心的问题：志愿服务是什么？和有偿工作有什么不同？参加之前应该了解什么？接着寻找可信的原始资料，记录标题、发布机构、日期和链接。

然后由人决定哪些问题值得回答，让 AI 协助整理中文初稿。编辑逐条检查重要事实、适用条件和来源，把“官方资料说什么”与“我们的通俗解释”明确分开。最后才是排版、试读、发布。

一本书不一定从一开始就完美。有人指出概念不清楚，可以改；来源更新了，可以补；手机上不好读，可以调整排版。好的数字出版不只是一次性的“发出去”，而是让内容有机会在之后继续完善。

这里最重要的不是会不会制作网页，而是选题、来源、理解、表达、核查、出版与修订这一整条编辑链。AI 能参与其中多个环节，却不应替代最终的事实判断和出版责任。

为什么把资料放在 GitHub，而不是只发到网站？

如果主要任务是写博客、发新闻、更新活动，WordPress 等内容管理系统非常方便。它们也能提供编辑权限和修订历史。GitHub 并非全面优于 WordPress，也不是所有读者都需要接触的工具。

区别在于工作重心。WordPress 通常围绕“把内容发布到网站”；GitHub 更适合把“源文件、修改记录、协作讨论与审阅过程”作为项目的一部分。公开知识库尤其看重这些过程，因为读者可能不仅想阅读，也想提出更正，甚至接手长期维护。

GitHub Pages 还能将符合要求的静态网页公开展示，让读者像访问普通网站一样阅读，不必注册 GitHub。但 Pages 不提供完整的会员、支付或数据库后台功能。具体选择应取决于项目需要，而不是追求技术新鲜感。

一个常见的组合是：在 GitHub 保存公开学习资料和编辑历史，通过阅读网页展示内容；另一个网站继续承担活动、服务和其他互动功能。它们可以互相链接，不必互相替代。

不会编程的人，怎样真正参与？

最容易开始的贡献，往往不是写代码，而是发现问题。比如你读到一篇文章，发现它引用的官方链接已经失效；或者有个专业词语让普通读者误解。把问题和具体位置告诉编辑，就是一次有价值的贡献。

再进一步，你可以推荐原始资料，整理几条读者常见的问题，请 AI 帮忙写中文摘要，或对照英文检查一段翻译。善于设计的人可以改善阅读体验；熟悉某个主题的人可以提醒作者遗漏了哪些重要条件。每种贡献都需要尊重来源和隐私。

愿意学习 GitHub 的人，可以通过 Issue 提建议，通过 Pull Request 提交供维护者审核的修改。但这些不是参与的门槛。一个项目也可以接受邮件、共享文档或其他约定渠道的建议，再由编辑整理进仓库。

多人合作并不意味着谁都能直接改掉正式出版内容。可以开放建议与讨论，同时保留必要的审核程序。这既保护资料质量，也保护参与者的劳动。

让知识可以被后来的人接着维护

一个知识项目最怕的情况，不是起步时只有几篇文章，而是过了一段时间，谁也不知道哪份文件是最新版、资料从哪里来、哪些内容需要复查。

所以，比“多写几篇”更值得养成的习惯是：为文章保留原始链接、注明最后核对日期、记录重要修改，并明确哪些内容仍有疑问。公开仓库能帮助保留这些痕迹，但不会自动判断来源可靠，也不能替你取得转载许可。

当最初的作者没有时间继续维护时，后来的参与者仍有机会理解这份资料是怎样形成的。这样的可延续性，是数字知识库区别于一次性分享的重要意义。

不过，公开不等于可以随意公开他人隐私、未授权聊天记录或受版权保护的完整作品。知识共享也必须尊重个人和原作者的权利。

从一件小事开始

不必立刻建网站，也不必今天就注册 GitHub。先找一篇你真正关心、来源可靠的公开资料，试着用自己的话写出它解决了什么问题，再记录原文链接。

如果愿意使用 AI，就请它协助整理成一张中文学习卡，然后自己对照来源检查：有没有遗漏限定条件？有没有把猜测写成事实？哪些话太难懂？

最后，把它交给一个愿意共同审阅的人。两个人能认真核查并改进一份资料，就已经开始了知识共建。等资料逐渐增多，再考虑用 GitHub 这样的工具长期保存、管理和公开出版，完全来得及。

技术的意义，不是让每个人变成程序员，而是让更多人有机会把自己理解的知识整理好，留给后来的人。
